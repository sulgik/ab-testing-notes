16 · LLM 시대의 실험: offline evaluation과 온라인 실험

책 밖의 주제 · 출력이 매번 다르고 정답이 없는 시스템을 어떻게 비교하나

진단 질문

  1. LLM 기반 제품의 실험이 전통적 A/B와 다른 점을 네 가지 들라.
  2. offline evaluation(벤치마크, LLM-as-a-judge)와 온라인 실험의 역할 분담은?
  3. "LLM-as-judge" 점수를 지표로 쓸 때 통계적으로 무엇을 확인해야 하나?
  4. 프롬프트나 모델을 바꾸는 실험에서 randomization unit을 무엇으로 하나?
  5. 벤치마크 점수 차이 2점이 의미 있는지 어떻게 판단하나?

1. 무엇이 다른가

차이내용실험에 주는 영향
출력이 확률적같은 입력에도 매번 다른 답. 온도, 샘플링"처치"가 하나의 고정된 variant이 아니라 분포다. 단일 사용자 경험의 분산이 크다
정답이 없다요약·대화·코드의 품질은 다차원이고 주관적지표 정의가 어렵다. 클릭·체류 같은 행동 지표가 품질과 어긋날 수 있다
변경 비용이 낮고 빈도가 높다프롬프트 한 줄 수정, 모델 버전 교체실험 수가 폭증한다. 오프라인 선별이 필수
비용·지연이 처치의 일부더 큰 모델은 더 좋지만 느리고 비싸다지연시간·비용이 guardrail이자 상충 변수다 (12회의 속도)
장기 신뢰 효과한 번의 심각한 오류(환각)가 신뢰를 오래 깎는다평균 품질뿐 아니라 꼬리(최악 사례)를 지표로 봐야 한다
공급자 변화외부 모델 API가 바뀌면 처치가 실험 중에 바뀐다모델 버전을 고정하고 기록한다

2. offline evaluation과 온라인 실험의 분담

offline evaluation온라인 실험
무엇고정된 입력 집합에 대한 출력 품질 채점 (벤치마크, 사람 채점, LLM-as-a-judge)실제 사용자에게 노출하고 행동·만족 지표 비교
속도·비용분~시간, 저렴일~주, 사용자 노출 비용
답하는 것"출력이 더 좋은가"(채점 기준 안에서)"사용자에게 더 좋은가, 사업에 더 좋은가"
한계입력 집합이 실제 분포와 다르다. 채점 기준이 사용자 가치와 다르다. 과적합(벤치마크에 맞춘 개선)느리고 비싸다. 품질의 어느 차원이 움직였는지 모른다
offline evaluation은 선별, 온라인 실험은 확정이다. 수십 개 후보를 오프라인으로 줄이고, 남은 소수를 온라인으로 확정한다. 중요한 것은 두 단계의 일치율을 추적하는 것이다. 오프라인에서 이긴 것이 온라인에서도 이기는 비율이 낮으면 offline evaluation(입력 집합이나 채점 기준)를 고쳐야 한다. 이것은 09회의 surrogate metric 검증과 같은 구조다.

3. LLM-as-a-judge 점수를 지표로 쓸 때

사람 채점은 비싸므로 다른 LLM이 출력을 채점하게 한다. 이 점수를 지표로 쓰려면 측정 도구로서의 성질을 확인해야 한다.

  • 타당성. 심사 점수가 사람 판단과 얼마나 일치하나. 사람 채점 표본과의 상관, 일치율. 일치가 낮으면 점수가 무엇을 재는지 모른다.
  • 신뢰성. 같은 출력을 다시 채점하면 같은 점수가 나오나(심사 LLM도 확률적이다). replication성이 낮으면 여러 번 채점해 평균하거나 온도를 0으로.
  • 편향. 심사 LLM이 긴 답, 특정 형식, 자기 계열 모델의 출력을 선호하는 것이 알려져 있다. 위치 편향(두 답을 비교할 때 먼저 나온 것 선호)도 있다. 순서를 바꿔 두 번 채점하는 등의 대책이 필요하다.
  • 처치와의 독립. 채점 기준이 처치가 바꾼 것에 민감하게 설계돼 있으면(처치가 길이를 늘렸고 심사는 길이를 선호) 점수 차이가 효과가 아니다. 01회의 "post-treatment variable" 논리.
  • 분산. 입력 수가 유효 표본이다. 입력 100개로 2점 차이는 보통 잡음 안이다. 입력별 paired comparison(같은 입력에 두 출력)로 분산을 줄인다. 01회의 paired 구조.

4. 온라인 실험 설계에서의 선택

  • randomization unit. 사용자가 대화 맥락에서 모델 변화를 눈치챌 수 있으면 사용자 단위. 단일 요청의 품질만 비교하고 사용자가 눈치채지 못하면 요청 단위도 가능하지만, 대화는 요청이 서로 의존하므로 대화(세션) 단위가 보통 최소다 (08회).
  • 지표. 행동 지표(재질문, 복사, 수락, 세션 길이)는 민감하지만 방향이 모호하다. "재질문"은 불만일 수도 관심일 수도 있다. 명시적 피드백(좋아요)은 희소하고 편향됐다. 보통 행동 지표 + 표본에 대한 사람·LLM 채점 + 지연·비용 guardrail을 함께 쓴다 (04회).
  • tail metric. 평균 품질 외에 "심각한 실패율"(환각, 유해 출력, 거부)을 guardrail으로. 이 비율은 작아서 power가 낮다. 사전에 MDE를 계산하고, 못 잡는다면 오프라인 red-teaming으로 보완한다.
  • 비용·지연 상충. 품질 +1%와 비용 +30%를 어떻게 비교할지 사전에 정한다. 환산율이 없으면 결정이 사후 해석이 된다.
  • variance reduction. CUPED(사용자 평소 행동)는 그대로 쓸 수 있다. 입력 난이도가 결과 분산의 큰 부분이면, 요청 단위 실험에서 입력 특성을 공변량으로 넣는다.

5. 에이전트와 평가 루프

  • 에이전트(여러 단계의 도구 호출)는 경로가 분기해서 "같은 입력에 대한 비교"가 더 어렵다. 최종 결과(과업 성공)와 과정 지표(단계 수, 비용, 되돌림)를 함께 본다.
  • 평가 집합이 제품의 실제 분포를 따라가야 한다. 실제 로그에서 입력을 표집해 평가 집합을 주기적으로 갱신하고, 어떤 입력에서 실패하는지를 세그먼트로 본다 (10회).
  • 평가 결과가 다음 변경을 만들고, 변경이 다시 평가되는 루프가 제품 개발의 중심이 된다. 루프의 속도와 신뢰성이 조직의 실험 성숙도(02회)에 해당한다.
  • 모델이 평가 집합을 "본" 적이 있으면(학습 데이터 오염, 또는 평가 집합에 맞춘 반복 수정) 오프라인 점수가 과대평가된다. 평가 집합을 분리해 두고(holdout), 온라인 일치율로 감시한다.

6. 다시, 통계는 같다

LLM이 바꾼 것은 "처치가 확률적이고 정답이 없다"는 것이지, 추론의 원리가 아니다. random assignment, analysis unit, 분산 추정, multiple comparisons, surrogate metric 검증, guardrail, interference(공유된 모델 서버의 지연)은 그대로 적용된다. 새로 필요한 것은 측정 도구(채점)의 타당성과 신뢰성을 먼저 확인하는 습관이고, 이것은 통계학이 오래 해 온 일이다.

확인 문제

Q1. 새 프롬프트가 벤치마크 200문항에서 72점 → 75점. 이 차이가 의미 있는지 판단하려면 무엇이 필요한가?
Q2. LLM-as-a-judge로 "답변 도움됨" 점수를 지표로 쓰려 한다. 지표 채택 전에 할 검증 세 가지.
Q3. 더 큰 모델로 바꾼 실험에서 만족도 +2%, 지연 +400ms, 비용 +40%. 출시 결정을 어떻게 구조화하나?
Q4. offline evaluation에서 이긴 변경 20개 중 온라인에서도 이긴 것이 6개다. 무엇을 의미하고 무엇을 고치나?
정답
  1. 문항별 paired comparison(같은 문항에서 두 프롬프트의 점수 차이)의 분산. 200문항이면 표준오차가 몇 점 수준일 수 있어 3점은 잡음 안일 가능성이 있다. 심사의 replication성(여러 번 채점), 문항 집합이 실제 분포를 대표하는지, 프롬프트가 벤치마크에 맞춰 조정됐는지(과적합)도 확인.
  2. ① 사람 채점 표본과의 일치(타당성) ② 같은 출력 반복 채점의 일치(신뢰성) ③ 길이·형식·위치 편향 확인과 대책(순서 바꿔 채점). 추가로 처치가 바꾸는 것(길이 등)에 채점이 민감하지 않은지.
  3. 사전에 정한 환산율로 통합: 지연 400ms의 만족도·이탈 비용(12회의 속도 환산율), 비용 +40%의 사업 가치 대비. guardrail(지연 상한) 위반이면 출시 불가. 대안으로 어려운 요청에만 큰 모델을 쓰는 라우팅을 실험한다.
  4. offline evaluation이 온라인 가치를 잘 예측하지 못한다(일치율 30%). 입력 집합이 실제 분포와 다르거나, 채점 기준이 사용자 가치와 어긋나거나, 오프라인에 과적합됐다. 실제 로그에서 입력을 재표집하고, 온라인 승자·패자의 출력 차이를 보고 채점 기준을 고친다. 그때까지 오프라인 승리를 출시 근거로 쓰지 않는다.
