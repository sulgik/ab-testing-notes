06 · 신뢰성 도구: A/A 테스트, triggered analysis, SRM과 guardrail

Kohavi 19·20·21장에 해당 · 결과를 믿기 전에 플랫폼을 믿을 수 있는가

진단 질문

  1. A/A 테스트는 무엇이고, 무엇을 잡아내나? 결과가 "유의"하게 나오면 무엇을 의심하나?
  2. SRM이 무엇이고, 왜 작은 비율 차이도 심각하게 보나? 흔한 원인을 세 가지.
  3. triggered analysis가 무엇이고, 효과 추정을 어떻게 바꾸나? 어떤 조건에서 편향이 생기나?
  4. 50/50 실험에서 control group 501,500명, treatment group 498,500명. SRM인가?
  5. 신뢰성 guardrail에는 SRM 말고 무엇이 있나?

1. A/A 테스트

처치가 없는 실험이다. 두 군을 무작위로 나누되 똑같은 것을 보여 주고, 지표 차이를 검정한다. 효과가 0임을 아는 상태에서 플랫폼이 무엇을 말하는지 보는 것이다.

무엇을 잡나

  • 분산 계산 오류. A/A를 수백 번 돌리면(또는 과거 데이터를 무작위로 반복 분할하면) p-값은 균등분포여야 한다. p < 0.05가 5%보다 훨씬 자주 나오면 분산을 과소추정하는 것이다. 흔한 원인: randomization unit과 analysis unit 불일치 (05회).
  • 할당 버그. 두 군이 실제로 무작위가 아닐 때. SRM과 함께 드러난다.
  • 로깅 차이. 두 군의 코드 경로가 달라 한쪽에서 이벤트가 더 찍히거나 덜 찍힐 때.
  • carryover. 버킷을 재사용하는 플랫폼에서 이전 실험의 효과가 남아 있을 때 (01회).
새 플랫폼, 새 지표, 새 randomization unit을 도입할 때마다 A/A를 돌린다. 플랫폼을 믿을 수 있을 때만 A/B 결과를 믿을 수 있다.

2. SRM: sample ratio mismatch

설계한 allocation ratio와 실제 관측 비율이 통계적으로 다르면, 결과를 믿으면 안 된다. 성가신 문제가 아니라 데이터 품질 실패다.

  • 검정: 카이제곱 적합도 검정. 플랫폼은 보통 p < 0.001에서 경고한다. 실험이 많아 거짓 경보를 줄이려는 것이다.
  • 왜 심각한가: 한쪽 군에서 사용자가 빠졌다는 신호다. 빠진 이유가 처치와 관련 있으면(예: 처치가 느려서 기록 전에 이탈) 남은 사용자는 더 이상 무작위 표본이 아니고, 효과 추정이 편향된다. 0.3%의 비율 차이가 몇 %의 효과 차이를 만들 수 있다.
  • 흔한 원인: 할당(해시) 버그, 처치가 로딩을 늦춰 기록 전 이탈, 봇 필터링이 한쪽에 다르게 작동, 한쪽 로그 유실, 처치의 영향을 받는 trigger condition, 리다이렉트 손실.
  • 대응: 결과 해석을 중단한다 → 날짜·플랫폼·브라우저·국가별로 비율을 나눠 어디서 차이가 생기는지 찾는다 → 원인을 고치고 다시 돌린다. 사후에 "빠진 사용자를 보정"하려는 시도는 대개 실패한다.

계산 예

50/50 설계, control group 501,500명, treatment group 498,500명. 기대값은 각 500,000. χ² = 2 × 1,500² / 500,000 = 9, 자유도 1, p ≈ 0.0027. 0.001 기준이면 경고가 안 뜨고, 0.01 기준이면 SRM이다. 경계 사례이고, 백만 명 규모에서 0.3% 차이는 우연으로 보기 어렵다. 경고가 안 떠도 세그먼트별로 한 번 확인하는 것이 맞다.

3. triggered analysis

배정된 사용자 중 실제로 변화를 본 사용자(triggered 사용자)만으로 분석하는 것이다. 결제 페이지를 바꾼 실험에서 결제 페이지에 간 사용자는 10%뿐이면, 나머지 90%는 두 군이 똑같은 경험을 했고 효과는 0이다. 이들을 포함하면 효과가 10배 희석된다.

전체 (ITT)triggered 사용자만
추정하는 것배정의 평균 효과 (희석됨)변화를 본 사용자에 대한 효과
power낮다높다 (잡음인 사용자가 빠짐)
출시 영향 추정그대로 쓸 수 있다trigger rate을 곱해 되돌려야 한다
편향 위험없다trigger condition이 처치의 영향을 받으면 생긴다
trigger condition은 처치와 무관하게 정의돼야 한다. "새 추천을 클릭한 사용자"는 treatment group에만 존재하므로 trigger condition이 될 수 없다. 올바른 조건은 "추천 영역이 노출된 사용자"처럼 양쪽 군에서 똑같이 판정할 수 있는 것이다. control group에서는 "처치였다면 변화를 봤을 사용자"를 counterfactual적으로 기록해야 하고, 이것이 instrumentation(11회)의 과제다.

triggered 집단에서 SRM을 다시 확인한다. 전체에서는 비율이 맞아도 트리거 집단에서 틀어지면 trigger condition이 처치에 오염된 것이다.

4. 신뢰성 guardrail

04회의 비즈니스 guardrail(지연시간, 오류율)과 별개로, 실험 자체가 유효한지를 보는 지표들이다. 하나라도 깨지면 다른 결과를 읽지 않는다.

  • SRM — 전체와 트리거 집단 모두
  • 군별 사용자 수의 일별 추이 — 특정 날짜에만 비율이 틀어지는가
  • 캐시·쿠키 비율 — 한쪽 군만 쿠키가 더 자주 리셋되면 "신규 사용자"가 늘어난 것처럼 보인다
  • 로그 중복·누락률 — 02회의 "너무 좋은 결과"의 가장 흔한 원인
  • outlier 비중 — 상위 0.1% 사용자가 지표 변화의 대부분을 차지하는가
  • treatment group·control group 코드 경로의 성능 차이 — 처치가 느리면 느린 것 자체가 효과를 만든다 (12회의 속도)

확인 문제

Q1. 과거 데이터를 1,000번 무작위 분할해 A/A를 돌렸더니 p < 0.05가 12%다. 가장 유력한 원인과 확인 방법은?
Q2. treatment group이 새 자바스크립트를 더 내려받아 첫 화면이 200ms 느리다. 어떤 신뢰성 문제가 생길 수 있고, 어느 지표에서 보이나?
Q3. "treatment group에서 새 배너를 본 사용자 vs control group 전체"를 비교하면 왜 틀리나? 올바른 trigger condition은?
Q4. trigger rate 20%, 트리거 집단에서 전환 +5%. 전체 출시 시 전환 변화의 대략값은?
정답
  1. 분산 과소추정. randomization unit(사용자)와 analysis unit(세션·페이지뷰)가 다를 가능성이 크다. 사용자 단위로 집계하거나 delta method로 다시 계산해 A/A를 재실행한다.
  2. 느린 사용자 일부가 로딩 전에 이탈해 기록되지 않는다 → treatment group 사용자 수가 줄어 SRM. 남은 treatment group은 인내심 있는 사용자로 편향된다. SRM 경보와 일별 사용자 수 추이, 지연시간 guardrail에서 보인다.
  3. trigger condition이 treatment group에만 적용돼 두 집단이 비교 가능하지 않다(treatment group은 배너 영역에 도달한 사용자만, control group은 전원). 올바른 조건: 양쪽 군에서 "배너 영역이 노출될 위치에 도달한 사용자". control group에서도 그 도달 여부를 기록해야 한다.
  4. 약 +1% (5% × 0.2). 정확히는 트리거되지 않은 사용자의 전환율 수준에 따라 달라지므로 가중 평균으로 계산한다.
